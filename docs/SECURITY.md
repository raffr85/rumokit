# Trust model

**Status:** trust model for an instruction package with thin Claude Code and Codex bootstrap integrations.

## Reporting security concerns

Rafael Affonso maintains RumoKit. Use
[GitHub private vulnerability reporting](https://github.com/raffr85/rumokit/security/advisories/new)
for security-sensitive reports. This channel is enabled on the official repository.
Do not put exploits, private code, credentials, or personal data in public issues.

For ordinary installation or workflow problems, follow [CONTRIBUTING.md](../CONTRIBUTING.md).
This project does not promise a response deadline or certify host security.

## Current facts

- The repository contains portable Agent Skills and native Codex and Claude-compatible manifests. One `rumokit` installation supplies the skills and one `SessionStart` hook. The separate `rumokit-codex` adapter is retained for legacy installations only; do not install both with version 1.0.1 or later.
- The shared startup hook reads the bundled `use-rumokit` skill and emits it as session context. The legacy adapter reads one bundled static context file. Neither hook reads the user prompt, transcript, workspace, credentials, or network.
- Hosts decide how plugins are installed, reviewed, trusted, and injected. If an integration is absent, disabled, unsupported, or untrusted, routing falls back to native skill discovery. Neither hook blocks a recommendation or verifies that the model followed the context.
- The repository contains no MCP server, daemon, policy engine, telemetry client, or RumoKit-owned agent runtime.
- The package itself does not request, store, or transmit credentials. An activated skill may guide the host to use its native tools, subject to the host's permissions and the user's authority.
- Private task fixtures, prompts, oracles, and raw evaluation artifacts are not bundled. The validation report contains aggregate acceptance results and their limits.

These facts do not prove how a coding-agent host, model provider, command selected during a task, future MCP server, or CI runner will behave.

## Executable artifact constraints

Any executable RumoKit artifact must default to:

- local operation under the user's chosen host;
- least privilege and no product-owned repository credentials;
- explicit authority before destructive or externally visible actions;
- no RumoKit telemetry unless separately designed, disclosed, and opted into;
- artifact and evidence retention controlled by the user;
- functional capability probes before claiming observation, veto, approval, sandboxing, or confinement;
- failure states that say `UNVERIFIED` or `INCONCLUSIVE` instead of inventing assurance.

“No egress” cannot be promised by a skill or this repository. Network behavior depends on the model service, host, tools, adapters, package manager, and commands the user runs. A future artifact may support a verified no-network configuration on a named surface; the claim must remain that specific.

## Instructions are not security controls

Repository files, issues, comments, web pages, tool output, local skills, and agent reports can contain misleading instructions. Prompt rules can guide behavior but do not authenticate authority.

A hook is not a security boundary merely because it is registered. Unless a host proves fail-closed interception and the project functionally tests it, no adapter may claim enforcement.

Human approval is meaningful only when the approval channel is outside the untrusted model path and binds the exact action or artifact being approved.

## Probes are untrusted code

A visible probe, test suite, build, migration, or repository script can execute arbitrary project code. Future tooling must not describe a probe as safe merely because it came from the repository or was generated by an agent.

Use the host's containment that matches the risk, such as a disposable workspace, restricted credentials, filesystem and network limits, or CI policy. RumoKit reports observed controls, not controls requested only in prose.

## Public/private boundary

The public repository may contain product documentation, reviewed aggregate
results, and deliberately public synthetic examples or regression scenarios.
Label synthetic material as such and check that it contains no private inputs.
It must not contain:

- private source code or repository snapshots;
- private task prompts, patches, fixtures, transcripts, or raw traces;
- confidential evaluation answers or oracles reserved for blind testing;
- personal filesystem paths, private account details, quotas, tokens, or credentials;
- private review notes or results not approved for publication.

`.gitignore` reduces accidental inclusion; it is not proof of isolation. Before
publication, review the complete file set, diff, and Git metadata for private
material, including author and tagger email addresses.

During research, keep URLs, hostnames, repository and issue identifiers, and quoted content from private sources inside the trusted local or approved connector boundary. Public web queries must be reduced to the general technical question and stripped of private identifiers. A useful public source does not justify disclosing the internal context used to find it.

## Release bar

No future release may claim local-only operation, zero credentials, no egress, enforcement, or confinement until that exact property is probed on the named harness, surface, version, and configuration. Any adapter that executes code, observes tools, persists state, makes decisions outside the model, or intercepts actions requires a primary-source threat review and a dependency and supply-chain review.
